# Stage-3 dataset: contract

This is also the **AI input/output specification** the stage-2 review recorded as
absent. The dataset format is the contract: anything a dataloader needs to know
is here, and anything not written here is not guaranteed.

Generated by `dataset/build_dataset.py`. Read this before writing a dataloader —
several conventions are load-bearing and a few are counter-intuitive.

## The task

Given what a rasterizer can compute cheaply, predict what a path tracer produces
expensively:

| | Tensor | Shape | Dtype | Range |
|---|---|---|---|---|
| **Input 1** | `sharp.exr` — pinhole render, **linear radiance** | H×W×3 | float32 | `[0, ∞)`, unbounded |
| **Input 2** | `depth.npy` — planar z along the optical axis, metres | H×W | float32 | `(0, ∞)`, `inf` = sky |
| **Input 3** | `coc.npy` — **signed CoC radius, pixels** | H×W | float32 | `(−∞, ∞)` |
| **Input 4** | lens scalars in `sample.json` | — | — | see below |
| **Target** | `dof.exr` — thin-lens render, linear radiance | H×W×3 | float32 | `[0, ∞)` |
| **Baseline** | `gather-naive.exr`, `gather-weighted.exr` | H×W×3 | float32 | `[0, ∞)` |

All passes are pixel-aligned: same camera pose, same field of view, same film.

## Conventions that will bite you

**Linear, not sRGB, and not bounded by 1.** The EXRs are scene-referred radiance.
The café contains emitters whose radiance is far above 1.0, and those bright
out-of-focus highlights are precisely where the gather and the path tracer
disagree most. Do not apply a transfer curve, do not clip to `[0,1]`, and do not
train an L2 loss directly on raw radiance without a compressive transform — one
bulb will dominate the gradient. A log or `x/(1+x)` transform applied identically
to prediction and target is the usual fix; whichever you choose, record it.

**Sky depth is `inf` in `depth.npy`.** The production shader cannot take a
non-finite depth, so `build_dataset.py` substitutes `sky_depth_m` (recorded in
`dataset.json`, default `1e4`) *only* for the gather inputs and for computing
`coc.npy`. The stored depth keeps `inf`, so a dataloader can recover the sky mask
exactly with `~np.isfinite(depth)`. Decide deliberately what the network sees;
feeding it `inf` will produce NaNs on the first forward pass.

**CoC is a signed RADIUS, not a diameter.** Negative in front of the focus plane,
positive behind, zero at it. The circle of confusion is conventionally defined as
a *diameter*; passing it in as a radius doubles the blur, and that was a real bug
in this project's history. The `0.5` is explicit in the code for that reason.

**The CoC formula follows the Mitsuba `thinlens` sensor, not the textbook.**

```
coc_sensor = (f / N) · f · (z − s) / (z · s)          ← what the reference implements
coc_sensor = (f / N) · f · (z − s) / (z · (s − f))    ← textbook; WRONG here
```

The two differ by `s / (s − f)`, measured at **2.72%** on the stage-2
configuration. The labels use the first form, so they match the renderer that
produced the targets. Regression test: 50 mm, f/1.8, focus 1.887372 m, object at
10 m, 540 px high → **+6.7162 px**.

**The target is the thin-lens render.** The gathers are stored to measure
against, never as supervision. A model trained on gather output can at best learn
to reproduce that method's errors.

## Lens scalars

From `sample.json → context.camera`:

| Field | Meaning |
|---|---|
| `focal_length_mm`, `sensor_height_mm`, `f_number` | the lens |
| `focus_distance_m` | planar focus distance |
| `fov_y_deg`, `intrinsics_px` | `fx`, `fy`, `cx`, `cy` |
| `origin`, `target`, `forward`, `up` | extrinsics |
| `coc_diameter_px_at_infinity` | the background blur ceiling for this setting |

Feed them as constant channels or through FiLM conditioning. **CoC already
encodes the lens**, so a model given `coc.npy` has the lens information in
spatial form; the scalars are for conditioning and for analysis, not strictly
required as input.

## Layout

```
data/dof-v1/
  dataset.json                 full plan: config, all samples, splits, config_hash
  shard-0000.json              per-shard outcome: written / skipped / failed
  train/ val/ test/
    s1004_home_050mm_f1.4_teapot/
      sharp.exr       sharp.exr.json          input + seal
      dof.exr         dof.exr.json            target + seal
      depth.npy       coc.npy                 input
      gather-naive.exr(.json)                 baseline + seal
      gather-weighted.exr(.json)              baseline + seal
      sample.json                             provenance, timings, statistics
```

## Splits are disjoint by scene, not by sample

Two samples of the same café from different angles share furniture, materials and
light positions. Splitting per sample puts near-duplicates on both sides of the
train/test line and produces a validation score that means nothing. Splits are
assigned by **scene seed**; `dataset.json → config.splits` lists which seeds are
in which split. Do not re-split downstream.

## Provenance

Every image is sealed by `experiment_contract.seal` with the scene hash, the
camera hash and a hash of the full render context. `authenticate()` rejects a
file whose settings do not match. This exists because a resumed or re-sharded run
can otherwise pair a sharp image with a reference from different settings: the
images are the same size and look plausible together, so the failure is silent.

**If you move or regenerate files, keep the `.json` seals with them.**

## Configuration space

8 f-numbers (1.2 … 16) × 3 focal lengths (28, 50, 85 mm) × 3 views × 3 focus
targets × N scenes = **216 samples per scene**. At the default 12 scenes that is
2592 samples.

f/16 is included deliberately. It is nearly sharp and is the control: a model
that cannot pass a near-sharp image through is broken in an obvious way, and it
anchors the blur range at zero.

## Generating

```sh
python dataset/build_dataset.py --dry-run                      # plan only, no Mitsuba needed
python dataset/build_dataset.py --out /tmp/ds --preset smoke   # 160×96, 16 spp, local check
sbatch --array=0-63 renderer/mitsuba/hpc/dataset.slurm         # the real run
```

Check a compute node **before** submitting an array job:

```sh
python renderer/mitsuba/gl_context.py
```

That must report a vendor GPU renderer. If it reports `llvmpipe`, the GL driver
is not in use, the gather would take days, and `build_dataset.py` refuses to run.

Re-running is safe: a sample whose `sample.json` exists is skipped unless
`--overwrite` is given, so a timed-out array task resumes where it stopped.

## Known limitations

- **References are not convergence-certified.** `spp` is a budget, not a measured
  error bound. Stage 2 measured that the full-lighting café needed roughly
  **844,000 spp** for a qualified comparison at f/1.2 — far beyond a dataset
  budget. These targets are good renders, not qualified ground truth, and should
  not be described as the latter. A per-sample error bar would need two seeds per
  target and is not currently generated.
- **One scene family.** All samples are the same café builder with different
  seeds. Generalisation beyond café interiors is untested.
- **Glass and metal are present**, so some targets contain refraction and
  specular transport that no single-layer gather, and possibly no image-space
  network, can reproduce from a pinhole input. This is deliberate — it is the
  honest difficulty — but expect those pixels to dominate the error.
- **The beauty passes use a Gaussian reconstruction filter while the G-buffer
  uses one box-filtered sample per pixel.** They share image coordinates but not
  silhouette coverage, so depth and colour disagree by under a pixel at edges.
